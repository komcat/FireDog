# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**This file is the map and the rules.** The detail lives in `docs/`, one topic per
file — open the relevant one *before* changing that subsystem. What is kept here
is what prevents a mistake when nothing else has been read.

## What FireDog Is

A **lightweight C++20 controller for a universal active-alignment machine**. Real drivers exist for: Basler camera (Pylon), Keithley 6482 picoammeter and Keithley 2602B SMU (VISA, both behind `ISmu`), Thorlabs CLD101x laser/TEC (VISA), UNI-T UDP3305S 3-channel PSU (VISA), CCS PD3 LED lighting controller (raw TCP), PI hexapods + ACS gantry (motion), FASTECH Ezi-IO + WAGO Modbus (digital IO), plus synthetic pneumatic slides, an IO watch, and a safety watch built on the IO fleet. Nothing real is still simulated.

Sibling projects under `..\komcat\` are the reference implementations for the same domain: **`bobcat_engine`** (mature Qt6 version, richest domain map) and **`BobDog`** (a raylib+rlImGui version — useful for how the PI/ACS/Pylon SDKs get wired into CMake). FireDog deliberately does **not** use raylib.

Entry point is `FireDog.cpp` → `firedog::App::Run()`, whose main loop is `while (!host_.ShouldClose())` over the GLFW `GlHost`. Everything is in namespace `firedog`.

## Build

```bash
cmake --preset x64-debug             # configure (presets: x64/x86 × debug/release)
out/build/x64-debug/FireDog.exe      # run the client
out/build/x64-debug/FireDogRig.exe   # console hardware bring-up rig
```

Three targets: **`firedog_hw`** (static lib — `src/core` + `src/hardware` +
`src/vision` + `src/workflow`, and where all vendor-SDK gating lives),
**`FireDog`** (the GUI client), **`FireDogRig`** (the console rig, sources in
`tools/rig/`).

CMake + Ninja + MSVC, **Windows only**. Deps come from `FetchContent` (first configure needs network). Vendor SDKs are optional, each gated by a compile def (`HAS_PYLON`/`HAS_VISA`/`HAS_PI`/`HAS_ACS`/`HAS_EZIIO`/`HAS_HALCON`) with a simulated stub fallback, so the build always stays green — details in `docs/build-and-sdks.md`.

**The user compiles and tests themselves** (global preference). Do **not** run `cmake --build …` or launch the app — `cmake --preset` is fine; leave building and running to the user.

## Rules

Breaking any of these is a defect, not a style choice.

### Layering
- **Dependency direction is one-way: UI → workflow → hardware.** The UI never touches a device directly.
- **Layer 1 owns, layer 2 drives, layer 3 renders.** `HardwareManager` is the sole owner of every device. Do **not** move device ownership or connect logic into `App`.
- Connection state is `ConnState` — never reintroduce a parallel int-status encoding.
- Exception, deliberate: **`SafetyWatch` is owned by `Workflow`**, because its callback stops motion through the Workflow object and so must die first.

### Threading
- **No blocking call on the UI thread.** Engine waits go through `ExecutionContext::Sleep/WaitUntil` (every wait has a timeout) so Stop interrupts within one poll interval. `PneumaticSlide::ExtendAndWait`/`RetractAndWait` block — never call them from the UI.
- **No detached threads, ever.** Each engine runs ONE worker; the dtor stops and joins it. The one scoped exception is a recipe's `parallel` block: `StepRunner::ExecParallel` forks one thread per mover lane and JOINS every one before the block returns (`JoinAll`), so the worker still owns the run and Stop reaches each lane through the same `ctx.ShouldStop()` its waits poll. The callbacks (`onStep`, `onLeafDone`, `onBeforeLeaf`) never leave the calling thread.
- `ProductSession` is **UI-thread only, no locks** — engines receive a *copy* through `Env` at Start. That copy-at-Start IS the concurrency contract.
- The session never calls back into the UI; `App` re-points its own selections after a load.

### State & documents
- Build a run's `Env` **only** via `session_.MakeRecipeEnv()` / `MakeLuaEnv()` — hand-copying the fields is how a caller forgets the library and breaks `sub_recipe`.
- **A Draw function must never mutate the document.** Seeding/derivation belongs in `App::Update` or the session.
- Runtime-writable JSON follows the `xxx.local.json` → `xxx.json` fallback (local files gitignored).
- **A build never overwrites the exe-side `config/`** (`cmake/StageConfig.cmake`): a file is staged only when MISSING, so the exe-side copy is the MACHINE's config and the repo's is the default for a fresh build tree; only `config/scripts/` is refreshed every build (standard scripts track the commands). A change every machine needs goes into the repo file AND, by hand, into each machine's copy — the build prints which files differ. The release zip takes the REPO's `config/`.
- Never hard-code DataBus topic strings; they live in `core/Topics.h`.
- **A position change is recorded by DIFF in `ProductSession::SavePositions`, never at a call site.** The journal (`core/PositionHistory`) compares the map being written with `positionsBaseline_`; a caller only says *why* (`SavePositions("hand")`, the teach drain's `recipe <name>`), never *what*. Hidden positions are not journalled. Restore goes through `RestorePosition`, which saves like any edit and so appends its own entry — a restore that rewrote the journal would lose what it restored from. `App::LogIn` is the one writer of the journal's author, as it is of the DUT operator.

### Orchestration
- **A slot is a TREE of nodes (recipe | folder), and a FOLDER is the unit of repetition.** Loops are expanded into the flat queue by `BuildRunQueue` at Start — `ProgramRunner` never learns what a folder is, so Stop, progress and `$run` keep exactly one implementation. Hence the ceilings (`kMaxQueueItems`, `kMaxDepth`): a mistyped loop count must be refused before the machine moves. There is no "repeat rows 1-3" range loop — a range is a second way to say what a folder says, and it breaks on the first reorder.
- **A node is addressed by its UID, never by an index.** An index into a tree means nothing once a folder above it opens, closes or moves; `deckNode_`, the run marks and the organizer's selection are all uids.
- **A deck cycle's node marks are RUNTIME state, cleared only by running the start node.** `deckMarks_` never reaches the program file or UiSettings: a green tick describes one physical part, exactly like a live frame, and a persisted one would read as a licence to skip a step. `AdvanceDeckCycle` steps off `runNodeUid_` — what was LAUNCHED — never off `deckNode_`, because the deck stays clickable during a run. The cycle never blocks a run: it is an aid, not an interlock.
- **Program editing lives ONLY in the Program Organizer window** (`ui/windows/WndProgramOrganizer.cpp`); the Run deck is read-only. Its drops are DEFERRED to `ApplyOrgDrop` — inserting inside `DrawOrgTree` reallocates the vector the recursion is walking. Its editing surfaces gate on `orch_.Busy()` and it raises no modal: it can be open on a second monitor while a worker is blocked on the always-on-top prompt window. It shows TWO slot panels (each with its own slot + selection, addressed by `panel` 0/1) and an aisle that moves or copies a selection across; **every copy — Duplicate, Dup Slot, Copy, Paste, Copy > — goes through `CloneNode`/`CloneSlot`/`CloneProgram`, which mint fresh uids all the way down.** A uid is an identity (selection, run marks, cycle states, the DUT's program reference); a copy that kept one is two nodes answering to one name.
- **Every Run/Go surface gates on `orch_.Busy()`** — never on a subset of the engines. The program runner goes momentarily idle between queue items, so checking the engines alone lets a second run slip in.
- **A `parallel` block holds MOVERS only, dealt into ONE LANE PER DEVICE, and runs each item's ordinary command unchanged.** Lanes run at once; within a lane the items run in the order written; the block ends when the last lane is done. There is NO barrier inside a block — a barrier between two sets is a second block. A command opts in by setting `CommandSpec::parallelBy` (the name of its device param) and nothing else — the same shape as `TeachParam()` for teach mode. It may do so only if it touches nothing shared but its own controller and the `ExecutionContext`: `move_relative_global` stays out because `JogGlobal`'s jog-track map on `Workflow` is unguarded. Do NOT add an issue/wait split to the movers to avoid the threads — that is a second copy of `MoveWithApproach`'s load-bearing ordering. The validator refuses structure inside, a non-mover and `teach`; a child's `on_error` acts within its lane, the block's on the block. A teach-mode run turns the block into a `group` (`MakeTeachRecipe`), because two Manual Adjust windows are two stages for one operator.
- Recipes never connect hardware; validation at Start requires devices already `Connected`.
- Ctx does **not** flow between recipes — cross-recipe data goes through the DUT or the DataBus.
- `$`-prefixed DUT keys are reserved for events.
- **Teach mode is a recipe TRANSFORM plus a `teach` param on the movers; the engine has no teach mode.** `RecipeEngine::Start` hands its private copy through `MakeTeachRecipe` (`command/TeachMode.h`): non-movers are DISABLED (never removed — step paths must keep their indices), movers get `teach = true`, loops run once, an `if` becomes then-then-else, `stop_recipe` is off. `StepRunner`, `ValidateRecipe` and `CountLeafSteps` stay untouched — a second filter in the runner would be a second answer to what a teach run executes. Save writes **by uid** (`RecordPositionByUid`) and never creates. A teach run writes no `$run`, sets no deck mark and never advances the cycle; the flag is never persisted and `LogOut` clears it. A command becomes a teach mover by declaring `TeachParam()`, nothing else.

### Dispense needle
- **The camera→needle offset lives in `gantry-main` AXIS space and never goes through `AxisTransform`.** Camera and needle ride the same device, so the delta between them crosses no frame — and `gantry-main`'s transform inverts Z (`M33 = -1`), so an axis value issued as a global delta descends when it meant to retreat. `read_position` reads axis, `move_axis_to` commands axis, `NeedleCal` stores axis.
- **Which way Z counts is derived, never assumed.** `NeedleDownSign` is `sign(dz)` from the measurement. bobcat hardcoded "+Z is down"; that is correct on one machine and a needle crash on the next.
- **`dz` is an offset from a FOCUSED camera Z, not a height.** An absolute touch height only describes the surface it was taught on, which is why bobcat needed a `dispense_z_<uid>.json` per point. With `auto_focus`, one offset serves every point.
- **The calibration is machine-level and its persisted record IS the licence to move** — unlike a taught frame, which describes one part and is cleared at every boundary. It goes stale for exactly one reason: the needle was changed. A worker queues it (`Workflow::QueueNeedleCal`); only `App::Update` writes `config/needle_cal.local.json`.
- **`needle_calibration.lua` is STANDARD; `dispense_procedure.lua` is deliberately NOT.** Where the needle is, is a fact about the machine and every product must measure it identically. How much glue goes where is a fact about the product, so its own copy must keep winning.

### Device registration
- **`R` comes from `motion_transforms.json` (`M_ref * M_dev^T`) and `rotSource` says so.** Those entries are hand-typed ±1 permutations: exact for a device bolted square, approximate otherwise, and the error vanishes at the taught point and grows with distance from it — so it reads as drift rather than as an untested assumption. That is a fair deal for an APPROACH and a bad one for anything else. Never let a reader mistake it for a measurement; `rotSource` is the seam a measured rotation would arrive through.
- **The axis triad is never assumed right-handed.** Every matrix in the shipped transforms file has `det = −1`; controller sign conventions are not consistently handed. `DeviceRegSetRotation` orthonormalises while PRESERVING the handedness it was given, `R` may be improper, and `R^T` is still its inverse either way. Forcing a proper rotation inverts one axis of every answer.
- **`t` is measured by IMPRINT.** Touch the tool onto a coupon and mark the corners: the contact point by definition, on a flat surface, which is the best case for both the focus metric and the crosshair — where a pick on a curved tool lands on its silhouette. It needs **no `dz`**: the reference Z of a point is already "the gantry Z that focuses on it", so the focused view over the coupon hands the tip's Z straight back.
- **`R` belongs to the MOUNT, `t` belongs to the mount AND the tool — hence two dates.** A changed gripper invalidates `t` alone and costs one imprint; `regAt` and `tipAt` are stamped separately so the page can say which half is old. Teaching a tip clears `verified`.
- **There is no width check on the imprint.** An earlier version measured the mark's width and refused the teach against a typed tool width; the width of an imprint is a fact about the coupon and the ink, not the tool, so it refused good picks and was removed. The tool's **footprint** (`toolWmm` × `toolLmm`, reference X × Y) is TYPED into the record and only ever DRAWN — a box centred on the predicted tip, turned by the device's live **U**, on the Aux view, the Registration page and the Gripped Object page. Nothing refuses on it and nothing moves by it; `0` draws nothing.
- **A registration is not verified by predicting at the pose its tip was taught at** — that returns the measurement by construction. The check drives to `imprintPose + (dx,dy,dz)` and `verified` stays false when all three are zero, however small the residual. With a typed rotation this check is the ONLY thing on the machine that ever measures what the assumption costs.
- **Teaching is the PAGE; recipes get the consuming end.** Every step needs an operator placing a coupon, jogging a tool into contact and marking a mark — there is nothing to automate, and a second way to create a registration is a second answer to where the tool is. The three teachable poses live IN the record, never in saved positions: those belong to the product document and this is machine state. A pose may be *sourced* from a taught position for convenience, but the picker resolves it to COORDINATES on the spot — a record holding a position uid goes blank the moment another product is loaded. `StoreDeviceRegPose` is the one writer for both paths.
- **A tip that cannot be predicted publishes NOTHING** on `tip/<device>/…` — no stale value, no guess. A readout frozen at the last good number is how a rotated hexapod goes on looking placed. The reason is logged on the edge, never per frame.

### Gripped objects
- **A grip profile is PRODUCT state; a registration is MACHINE state.** A lens is part of a product and its detector is cut from a picture of that product's part, so a profile lives in `{uid}.grips.json` and its inspect pose in the product's own positions — the exact opposite of `DeviceReg`, whose three poses stay in the record for the same reason inverted.
- **The offset is `object − tip`, and only ever a DELTA.** Both terms are in the reference device's axis space, so the origin cancels and the result crosses to a device that has never shared one with the camera. The gripper-axis form is `DeviceRegSolve(object) − DeviceRegSolve(tip)`, never a hand-rolled `R^T`: `t` cancels between them and `DeviceRegSolve` stays the one place a matrix is multiplied.
- **A run never adopts its own measurement.** `ApplyGripResult` writes `last*` and never `ref*`. Adopting a reference means an operator looking at a grip they believe is good and saying so; a run that promoted its own number would make every grip a good grip.
- **There is no size check.** The manual marks' separation and a circle's radius both describe the picture, not the part — an edge the operator could see, a contrast the model was taught on — so a "measured width" checked against a typed size refuses good grips on lighting. The profile judges the offset and nothing else.
- **`grip_move_to_camera` moves on what THIS run measured.** The offset comes from ctx (`<prefix>_dx/_dy`), never from the profile's `last*` (a different pick) or the engine's copy of the document (taken at Start). Its target is `camera − offset` applied to the TIP, so it assumes the object sits at the tip's height; `z_offset_mm` stands the tip off the focused plane, not the object. It goes through `PrepareRegMove`/`ApproachRefPoint` (`command/RegApproach.h`) — never a second copy of the registration's refusals.
- **No reference offset means no PASS** — the measurement is still reported, `ok` is false and `_why` says why. A default pass is how an unchecked profile ends up trusted.
- **A profile's OUTLINE is drawn and never judged.** `outWmm` × `outLmm` plus an anchor (`anchorDx/Dy`, point − centre in the box's own frame) says what the object looks like around the point that was measured on it; the page and the Aux window hang it off that point (marks' midpoint while teaching, else tip + last offset, else tip + reference), turned by the device's live U like the tool's footprint. Both go through `DrawWorldBox` (`ui/Widgets`) — the anchor is applied in SCREEN space after the spin, so a second projection would put the box off its point. Nothing reads it back; the size rule stands.
- **Rotation is handled by the inspect pose, not by a guard**: it carries U/V/W, so driving there restores the pose the reference was taught at. A profile without one measures the tool where it finds it, and both the page and the script say so instead of refusing.

### Waffle trays
- **A tray's three corners are COORDINATES in its device's axis space, never position uids, and `TrayCellPose` (`core/WaffleTray`) is the one place a cell is computed.** The page's tooltip, `move_to_cell` and the cursor's walk all call it. The `or taught...` picker resolves a saved position to coordinates on the spot (`TeachTrayCorner` is the one writer). Changing the tray's device CLEARS the corners: the same numbers on another controller are a different place.
- **A tray's USED cells (`usedCells`, the cavity is empty) are PRODUCT state saved with the record; the `Workflow` cursor (`TrayNext`/`TrayConsumed`/`TraySeed`) is its live, thread-safe MIRROR.** An operator marks cavities on the page and a restart mid-tray must not start the next recipe at (1,1). Seeded from the document at product load / new product; a run's `tray_next`/`tray_reset` moves the cursor and queues the change (`QueueTrayUsed` → `TakeTrayUsed`, drained in `App::Update` into `ProductSession::SetTrayCellsUsed`, which saves on the spot); the page writes both through `App::SetTrayCellsUsed`. Never write `usedCells` or the cursor alone. NOT cleared at program start or DUT open — a program takes one cell per part across slots. `TrayNext` picks, consumes and queues under one lock.
- **`move_to_cell` is neither a teach mover nor a parallel mover.** A cell has no position row for a teach to write into (re-teach a corner instead), so it declares no `teach` and a teach-mode run disables it. `parallel` deals lanes by the value of a DEVICE param and this step's device is inside the tray record, so `parallelBy` stays empty and the validator refuses it in a block. A missing `row_key`/`col_key` FAILS rather than falling back to the typed value; a disabled cell FAILS unless `skip_disabled`, which reports `<prefix>_moved = false` — a move that silently did nothing looks exactly like one that arrived.
- **The page is Technician**, deliberately: a corner is a raw axis reading into the product document, exactly a Motion-page saved position. Every Go is behind the jog arm and `orch_.Busy()`. **The floating Waffle Tray window (`WndTray.cpp`, `kRoleTray` = Operator) draws the SAME grid through `App::DrawTrayGrid`** — a click must mean one thing in both places. The ACTIVE cell (`Workflow::TrayActive`, what `move_to_active_cell` drives to) is runtime state with two writers, a grid click and `tray_next`; the click stays live while a run is blocked on a prompt (that is the point), the marks and disables lock on `orch_.Busy()`.

### Mosaic
- **The canvas is the camera's pixel frame** (`g = g0 + M·c`, `vision/MosaicLayout`), so a tile is a pure translation and is never resampled — not to draw it, not to export it. A rotated camera changes `M` and nothing else. `PlanMosaic` is the one place a walk is laid out and `MosaicAreaValidate` the one refusal; the page's preview and `mosaic_capture` both call them.
- **A tile is placed by its MEASURED pose** (the axes after settling), never the commanded one — the difference is exactly what a commanded placement stitches into the seams. Both are kept in `mosaic.json`.
- **Mosaic areas are MACHINE state** (`config/mosaic.local.json`, the page is the only writer, saved on every change), not product or DUT state; the pictures go to the operator's save folder (default `C:\mosaic`). The capture reads the FILE at Start, which is why every editing surface gates on `orch_.Busy()`.
- **One writer per file in a mosaic folder**: `mosaic.json` + `tiles/` = `mosaic_capture`; `annotations.json` = the page (UI thread); `placement.json` + `export/` = `MosaicWorker`. Annotations are CANVAS px only — a gantry coordinate is derived through the record's `M` each time, never stored beside it.
- **The capture is a command run as a one-step recipe** (the quick-autofocus pattern), not an engine: Busy, Stop and the safety abort come with it. Do not add a second capture path. `mosaic_calibrate` is the same shape. **A measured camera map is a PROPOSAL** — both routes (the stepping command via `QueueMosaicCal`, and the worker's fit to a mosaic's seams) end in `App::ProposeMosaicCal`, and only the Admin's Apply on the Camera map section writes `mosaicCfg_.cal`. Never apply a measurement blind; never touch `hardware.json`'s `pixel_to_mm` from here.
- **The viewer never holds the picture as one texture.** Tiles are drawn at 1/16, 1/4 or full resolution by zoom; the bigger two are decoded by `MosaicWorker` (one owned thread, joined in its dtor) and paged LRU in `App::UpdateMosaic`. A texture drawn last frame is never evicted. No PNG decode or encode on the UI thread.

### Users & access
- **An employee number is an identity; a level is a property of that number.** The number, its level and its password are registered together by an admin in the User Manager — there is no shared per-level password and no self-service password change, because a credential that can be lent names a person who was never there.
- **The roster lives in `products/employees.json`, NEVER in `config/`.** A fresh build tree (or a release zip) carries the repo's `config/`, so a roster there would be lost with the build folder. For the same reason it takes no `xxx.local.json` pair: there is no shipped default to fall back to.
- **`MinRoleFor` defaults to Admin.** A page not named in the table is locked until somebody grants it — the only default that cannot fail open. The split is by what a page WRITES: Technician uses what the machine knows (motion, recipes, diagnostics), Admin teaches it (frames, detectors, needle, device registration, transforms, scripts).
- **`SwitchPage` is the enforcement; hidden menu items are courtesy.** Every switch already routes through it, so a surface that forgets to check still cannot land above its level. Gate a click *early* only when it mutates state before switching (the Run deck's right-click, and the four `Open*` teach helpers, which set up a model/marks/selection first).
- **A page gate does not cover a WINDOW or a shared block.** The Aux window is `kRoleAux` (Operator) because it monitors — but everything on it that MOVES (Arm jog, Z arrows, click-to-move, Autofocus) is `kRoleJog`, or it is a way around the Jog gate. Click-to-move is checked at the checkbox AND at the click handler because `enableClickMove_` is persisted in UiSettings. `DrawDutBlock` is shared by Overview and Run, so its Explorer shortcut is Technician: on an Operator's station it is the one control that leaves the application.
- **`LogOut` clears `jogArmed_`.** An armed jog inherited by whoever signs in next is the opposite of what the arm is for. `manual_adjust`'s jog stays ungated on purpose — a recipe step asked *this* operator to nudge the part and the run is blocked until they do.
- **The login gate is not a `Page`** — it draws instead of the whole main window, so no menu, F-key, strip button or floating window exists until somebody signs in. `Update` still runs, so hardware connects during login.
- **Sign out is refused while `orch_.Busy()`**, which is also what stops the gate appearing mid-run and blocking the always-on-top prompt window — the same reason this layer raises no modal.
- **`App::LogIn` is the ONE writer of `DutSession::SetOperator`.** The record carries the operator top-level AND as a `$operator` entry at open/handover AND on every `$run`: one record can span a shift change.
- Passwords are **plaintext, on purpose** (a roster repairable with Notepad beats resistance to someone who already owns the PC). The built-in `admin` / `iamyourfather` is checked before the roster so a corrupt file is never a lockout, and cannot be registered over.

### Hardware
- Port hardware code from **`bobcat_engine`**, not BobDog. Read the matching adapter in `..\komcat\bobcat_engine\include\` and port its actual SDK calls.
- All drivers are PIMPL: **vendor headers never leak into ours**, and each has a same-API simulated stub for when the SDK is absent.
- **IO pin addressing is normalized: bit i == pin i for BOTH inputs and outputs.** Vendor bit layouts are translated inside the driver; a shifted value must never cross the interface.
- **The current stream has TWO drivers behind one interface: `ISmu`.** `keithley_6482` (SCPI, GPIB/USB) and `keithley_2602b` (TSP, LAN) are picked by `type` in `hardware.json`, and `Workflow::LaunchKeithleyConnect` is the ONE place a concrete meter is constructed. Everything above layer 1 — the `keithley_*` recipe commands, the `keithley/ch1|ch2` topics, the page, the chart — stays model-agnostic; adding a third meter must not add a second code path up there. Do not rename the commands or topics to match a model: saved recipes reference them by name.
- **Keithley 6482:** read with `:READ?` each iteration. Do **not** set `:INIT:CONT ON` or read with `:FETC?` (every `:READ?` then raises -213 and the stream stalls at 0 Hz), and do not add a fixed inter-read sleep. Sample rate is governed by NPLC, not the poll interval.
- **Keithley 2602B is a SOURCE-measure unit, so its output must be ON to measure.** A 6482 measures with its V source off; an SMU with its output off reads ~0 A, which looks exactly like a dark photodiode. `SetVoltageBias` therefore switches **every enabled channel** on (ch1 at the bias, ch2 at 0 V) — never make it bias ch1 alone to "match the 6482". It is TSP, not SCPI: `localnode.prompts = 0` must go out **before the first query** or `TSP>` tokens interleave and every read is one reply out of step, and NPLC is clamped to 0.001..25 because the instrument silently ignores an out-of-window value.

- **CCS PD3 lighting accepts ONE TCP client — always close gracefully** (half-close + drain; an abortive close can hold its only slot until a power cycle), and **`F000` is not dark: 0 % means `L0`.** Channels are FRONT-PANEL numbers (L1 = 1) everywhere above the driver. A colour call-out is resolved in exactly one place, `Workflow::LightTargets` over `core/LightCallout`; the UI sets lights only through `Request*` (the poll thread sends), never a blocking setter.
- **A detection model carries the light it was taught under (`VisionModel::lighting`) and a station has NO lighting and no fallback** — a model set to None leaves the light as it is. `Workflow::ApplyLighting` is the one implementation of an `AlignLighting`; a model whose light cannot be set fails rather than detecting under the wrong one.

### Vision
- **Auto-focus must never depend on HALCON.** The focus measure is plain C++ (`vision/FocusMetric`); a licence problem degrades inspection, never alignment. The Alignment Procedure's manual crosshair pick is under the same rule — it is ImGui over a Pylon frame and nothing more.
- **Feature detection DOES need HALCON, and says so.** `vision/HalconDetector` (circle/fiducial, gray NCC with an anchor, square corner) is the only feature detection in the build. `vision/ImageShift` (the mosaic's frame-to-frame registration: calibration and seams) is plain C++ for the auto-focus reason — it measures an offset between two pictures of the same patch, it finds no feature. Without a licence the teach window is disabled with `HalconEngine`'s reason shown verbatim and an `auto` station fails loudly at run time; it must never silently become a manual pick unless the procedure asked for that fallback.
- **The pre-process chain is applied in exactly TWO places**, both in `HalconDetector.cpp`: `Detect` (between the `RgbToGray8` crop and the method dispatch — every run-time caller funnels through `Workflow::Detect` to there) and `Teach` (the template is cut from the **filtered** plane, or NCC matches a raw patch against a filtered image and scores nothing). The teach page's preview and overlay go through the static `HalconDetector::Preprocess`; a second implementation of the three filters is how the picture starts disagreeing with the detector. The chain lives on the model, so a filter edit already invalidates the cached detector via the JSON stamp — but `VisionModelPatchKey` must carry `VisionFilterSummary` or a re-teach keeps showing the old thumbnail.
- **`RgbToGray8` (`vision/FocusMetric`) is the one RGB→luma conversion.** A second detector must not pick its own weights. It returns the CLAMPED ROI, and a detector must add that origin back — every `VisionDetection` coordinate is full-frame.
- **The Run page's image box is ONE parked frame (`Workflow::CapturedView`), a slot and not a queue** — a 5 MP frame is ~15 MB and the box shows one. `DrainCapturedView` must stay **after** the DUT-open edge in `App::Update`: that edge clears the box (a still shows one physical part), and a recipe doing `dut_open` then `dut_capture_image` lands both in one frame, so draining first lets the open wipe the picture the capture just delivered. `capture_view` deliberately needs **no** open DUT — reading the serial is how you learn which DUT to open.
- **`RecipeEngine::Status.ctx` is a LIVE snapshot, not a result channel.** The engine clears `runCtx_` before the state becomes `Completed`, so a UI that waits for Completed and then reads `Status.ctx` gets an empty map. Anything a command hands back after a run goes through a `Workflow` queue drained in `App::Update` (`TakeSavedPositions` / `TakeAlignResults` / `TakeVisionReliability`). **`Status.lastCtx` is the snapshot taken at that terminal boundary and is DISPLAY ONLY** (the Run page's Values panel): it exists because polling `.ctx` per frame misses a value written by the recipe's final step. Never make a command read it — two result channels will disagree about what a run produced. Its drain (`DrainCycleVars`) must stay **before** `orch_.programs.Tick()` in `App::Update`, or the runner starts the next queue item first and the edge is missed on every recipe but the last.
- **A detection model is PRIVATE to one alignment station AND detection tier, auto-named `vdet_<procUid>_<station>` (tier 1) or `…_t2`/`…_t3`** — the name is the ownership record, exactly like the private station positions. There is no model picker, no rename, no New/Duplicate/Delete: parameters and a taught patch only mean anything at the pose and exposure they were tuned at. Deleting a procedure must drop them (`DropAlignStationDetectors`), duplicating must copy them (`CopyAlignStationDetectors`).
- **A detection model owns its `.pgm`** (`<modelUid>.pgm` under `ProductSession::VisionDir()`). Deleting a model drops the file (`DeleteVisionModel`); duplicating copies it. The filename in the JSON is **relative** — an absolute path makes a product folder non-relocatable.
- **A taught frame can only be created one way**: `align_solve` → `Workflow::QueueAlignResult` → `App::Update` → `ProductSession::ApplyAlignResult`. The Alignment page runs the same script a recipe's `align_run` step does — do not add a second capture path in the UI.
- **A SAVED frame is a record, never a licence to move.** `align_apply`, `move_local` and the Alignment page's *Move here* consume the **live** frame (`Workflow::SetLiveFrame`/`LiveFrame`), which exists only for the session that taught it and is cleared at **program start, DUT open and product load**. A frame describes where one physical part sat; moving against a stale one looks exactly like a correct move and is wrong by however far the part shifted. Never make a run read `AlignProc::result`. **The one exception is opt-in on BOTH ends:** `align_run keep_frame` (→ `align_solve keep`) lets a frame survive a PROGRAM START only (`Workflow::CarryLiveFrames` marks it `carried`), and a consumer (`align_apply`, `nominal_point`, `move_local`, `move_to_nominal`) accepts a carried frame only with its own `use_kept_frame`. DUT open, product load and app close still wipe it — never widen a keep past those.
- **Across devices, an absolute position crosses ONLY through a verified `DeviceReg`, and only as an approach.** Without one, `AxisTransform` has no offset and the two origins have never been related, so **only a DELTA transforms**: measure the object, subtract in the frame (the origin cancels, the rotation must not), then map the vector with `Workflow::GlobalDeltaToAxes` — **not** `JogGlobal`, which collapses a direction to its dominant axis and would drop half a diagonal. With a registration, `move_to_point` may command a gantry-space point to a hexapod to get the tip **close**; the final placement is still a MEASURED delta (the gripped-object module: `grip_measure` then `grip_move_to_camera`), because a registration is a typed rotation plus one measured point and the target is ~20 µm. Never let a `move_to_point` stand in for the measure/correct step.
- **A nominal is LOCAL-ONLY, and can only be taught through a live frame.** `AlignNominal` stores `lx`/`ly` (O1); the machine midpoint beside it is a record. `AlignMachineToLocal` is an identity on an invalid frame, so teaching through one silently stores a machine coordinate that the next frame re-projects to nowhere — `SolveAlignNominal` refuses instead. Duplicating a procedure keeps its nominals and clears its `result`: the frame is per-part, the nominals are per-design.
- **A procedure's private positions are named `algn_<procUid>_…` and `hidden`** — `_<station>` for the two stations, `_<nomUid>_v` for a nominal's camera view. The name is the ownership record: deleting a procedure drops every one of them (`DropAlignStationPositions`, a prefix sweep), deleting a nominal drops its view (`DropAlignNominalView`), duplicating copies both — or hidden orphans accumulate where nobody looks. `CapturePrivatePose` is the only writer, so a re-teach keeps the uid. `hidden` is withheld from the recipe *picker*, never blocked at validation — an existing reference must still resolve.
- **The placement module is retired** (`place_*` commands, `placement_procedure.lua`, `place_demo.lua` removed); device registration + gripped objects replace it. `PageAlignPlace`, the nominal's `viewUid`/`camUid`/object-detector fields and `nominal_view` are leftovers slated for removal — do not build on them. A camera move onto a nominal is `move_to_nominal` (live frame, the procedure's own device only).
- **`alignment_procedure.lua` (and the rest `IsSystemScript` names) are STANDARD** (`command/ExecutionContext.h`): every surface runs the shipped `config/scripts/` copy, and a product copy of the name is ignored with a warning. They change with the commands they call — a fork keeps silently skipping the newest step. Do not add a launcher that resolves them off `session_.Scripts()`.
- **`vision/Halcon*.cpp` are the only TUs that include a HALCON header** (`HalconEngine.cpp`, `HalconDetector.cpp`), and nothing else may call HALCON without asking `HalconEngine::Instance().Available()` first. Probe the DLLs with `LoadLibrary` **before** any HALCON call — the SDK is `/DELAYLOAD`ed, and a missing delay-loaded import raises an SEH exception that `catch` does not handle.
- **Frame freshness uses `PylonCamera::FrameSeq()`, never `isNew`** — `isNew` is one-shot, so the first of two consumers eats it.
- Move waits live in `command/MotionWaits.h`. Do **not** write a second arrival/settle helper in a new command file; the two-signal settle rule is what makes a scan sample trustworthy.
- **The two-speed move has ONE implementation: `MoveWithApproach`** (`command/MotionWaits.h`), and every point-to-point move command goes through it. Its ordering is load-bearing and a second copy will drift off it: the travel leg arrives on a LOOSER tolerance, `WaitSettle` runs BEFORE the velocity change (PI rejects `VLS` mid-profile with GCS 1005), and `velocity_mm_s` is re-applied afterwards so the device is not left crawling into the next step. A half-configured approach (a zone with no velocity, or the reverse) **fails** — it is a full-speed arrival wearing the label of a careful one, and `ValidateParams` is per-parameter so nothing catches it at author time.

### UI
- **Page state stays an `App` member.** New file-scope *mutable* state in a page TU is a bug — UiSettings persistence and cross-page sharing both read App members.
- A helper lives in the file that uses it; it moves to `ui/Widgets.{h,cpp}` only when a second TU needs it.
- **`Widgets.cpp` is the only UI TU that includes `windows.h`**; **`WndPrompts.cpp` the only one that includes `imgui_internal.h`**. Keep both that way.
- **All page switches route through `App::SwitchPage`** (it owns the takeover/`prevPage_` bookkeeping and the dirty-recipe guard). Don't assign `currentPage_` directly.
- **A run outranks navigation, and no page may drive a run it did not start.** Changing pages mid-run must not raise a MODAL: a modal blocks input to every other window, including the always-on-top prompt / `manual_adjust` / align-pick windows an engine worker is blocked on — the operator then sees a prompt they cannot click while the machine waits. Hence `SwitchPage` skips the dirty-recipe guard while `orch_.Busy()` (the edits stay in memory and stay dirty). For the same reason the Recipe Editor gates its editing surfaces on `orch_.Busy()` — **not** `recipe.Running()`, which blinks false between a program's queue items — disables Step/Next while `programs.Active()`, and makes its Stop stop the *program*, never one recipe out of the queue.
- When moving UI code between files, keep window/child/label strings and call order **byte-identical** (ImGui IDs derive from the runtime stack, not source location), and never mix a move with an improvement in one commit.
- Dangerous actions stay gated behind their armed checkbox (IO outputs, pneumatics, jog, click-to-move).
- Put global style/color tweaks in `ui/Theme.{h,cpp}`, not in individual panels.
- **The script editor is ImGui's `InputTextMultiline` under a colour overlay, and the engine runs the FILE.** The widget's text is transparent; the page paints the coloured text into the PARENT draw list before the widget and sizes the widget to the whole buffer so the outer child scrolls both — draw the overlay anywhere else (foreground list, after the widget) and it lands over the selection or drifts from the caret. Escape in an InputText REVERTS the edit session, hence `ScriptEditorState::shadow`; ImGui fires ONE text callback per frame (Completion, else Edit, else Always), so key handling lives in one function both call. Run stays disabled while the buffer is dirty, or the debugger's line numbers describe a file nobody is looking at. Completion candidates come from `CommandRegistry::List()` + `LuaFdBuiltins()` (`LuaEngine.cpp`) — never a list typed in the UI.
- **Do not reintroduce raylib/rlImGui.** It is single-window by design, which makes a real second OS window impossible and blocks ImGui multi-viewport. Owning the GLFW host removes that ceiling.

### Project
- Windows-only, MSVC, C++20. Aim for `/W4`-clean.
- **Vendor-SDK gating belongs on the `firedog_hw` library, PUBLIC** — never on an executable, or the second exe silently loses a `HAS_*` def. New executables call `firedog_stage_runtime(<target>)` for the config/DLL staging.
- **`FireDogRig` is read-only.** It connects and reports; it must never gain a command that moves an axis, writes an IO output, or switches an output. Actuation stays in the client behind its armed checkboxes.
- **There is no automated test suite.** Verify by building clean, then running (simulated hardware today). Never claim "tests pass" or invent a test command.
