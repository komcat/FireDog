# Layer 2.5 — commands, recipes & the Lua tier

*The registry that feeds three clients (engine, editor forms, Lua bindings), the
execution model, and the scripted algorithms. Design rationale is split across
`docs/recipe-core-design.md`, `docs/recipe-editor-design.md` and
`docs/lua-tier-design.md`; this is the operational summary.*

## Layer 2.5 — Command layer (`src/command/`)

Design doc: `docs/recipe-core-design.md`. One typed **`CommandRegistry`** (name + `ParamSpec` schema + execute fn capturing `Workflow&`) feeds three clients: the **`RecipeEngine`** (implemented), the recipe editor forms (Phase B), and Lua bindings (Phase C). Recipes are nested-JSON step lists (`config/recipes.local.json` → `recipes.json`, or the product manifest's `recipes` role); control flow (`loop` count/while, `if/else`, `group`, `sub_recipe` cycle-checked, `stop_recipe`) is engine-native — the registry holds only leaf actions. The engine runs ONE worker `std::thread` (dtor stops + joins — no detached threads, ever), validates at Start (params, references, devices Connected — recipes never connect hardware), contains exceptions at step boundaries, and aborts on critical safety alerts. **No blocking command may run on the UI thread**; all waits go through `ExecutionContext::Sleep/WaitUntil` (every wait has a timeout) so Stop interrupts within one poll interval. `move_path` requires the device to already be AT `from` (strict start, no nearest-node snapping) and shares `BuildMapRoute` (`core/MotionMap`) with the Motion page's Go button — one planner, two executors (the UI `TickPath` state stays UI-thread-only; the engine drives legs itself). **`manual_adjust`** (bobcat's ManualAdjust, ported v1) pauses the run in a global jog window (NON-modal, kept always-on-top via `BringWindowToDisplayFront` — only the engine worker blocks; the rest of the UI stays usable for camera/jog/click-to-move): the worker blocks in an `awaitAdjust` hook (same handshake shape as the prompt — `ExecutionContext::AdjustRequest`, `AnswerAdjust`, pending state in both engines' Status), while the window jogs via `Workflow::JogGlobal` (step presets = the Jog window's `kSteps`, live positions via `RequestFastPoll`, per-axis enables, STOP, safety-inhibit notice); OK continues (optional `ctx_prefix` records the confirmed position as `<prefix>_<axis>`), Cancel fails the step. Scripts get `fd.manual_adjust{...}` from the generated bindings. The **Recipe Editor** (View menu, full-page like the other editors; design in `docs/recipe-editor-design.md`) is the authoring+run surface: recipe list CRUD, step tree with palette/move/delete, schema-driven forms generated from `ParamSpec` (`DrawParamWidget` — a new command gets a working form for free), shared condition editor, Save to the product recipes file or `config/recipes.local.json`; the executing step highlights via `Status.stepPath`, and the recipe `prompt` window is global (drawn from `DrawMainWindow` like the safety alert; non-modal + always-on-top like `manual_adjust`). `App` owns registry+engines as ONE member — `command/Orchestration.{h,cpp}` (`orch_.registry/recipe/lua/programs`, plus `Busy()` and `StopAll()`) — declared AFTER `workflow_` (destroyed first, like `SafetyWatch`).

**Lua tier** (`command/LuaEngine.{h,cpp}`, design in `docs/lua-tier-design.md`): plain `.lua` programs (product `scripts/` dir, else `config/scripts/`; authored externally — an in-app VS-Code-style editor is parked as future work C4 in the design doc) run through bindings **generated from the same registry** — `fd.<command>{named=args}` validated by the same `ParamSpec` schemas, plus `fd.read/ctx/sleep/log/logf/prompt/input/positions/clock` and `fd.param(name, default)` — the recipe→script parameter-injection convention: recipes set ctx keys (`ctx_set` steps, typically grouped as "<algo> parameters") before `run_script`, the script reads them with defaults and logs each resolved value. Sibling algorithm script `config/scripts/raster_scan.lua` (bobcat GridScan port): serpentine area scan for first-light search — slow axis one-sided from start (`raster_slow_dir`, default X−), fast axis centered ±half-span (default Y), absolute grid targets off the start pose, same fresh-sample measure + exit-threshold stop-and-stay as the align script, returns to the best node otherwise; signal-gated cycle cuts: row-peak early stop (rows past the spot are dark) and fast-axis tracking (next row sweeps a narrow window around the previous row's peak) (`raster_*` params/ctx results, `rast,` trace lines). Both scripts also front as typed leaf commands (`xcan`, `raster_scan`, category Motion, in `CommandsSystem.cpp`): the step form's params are injected as the script's ctx keys (other `align_*`/`raster_*` keys ctx_set beforehand still pass through `fd.param`), then the file runs inline via `RunLuaFile` — exit targets are entered in **uA** (×1e-6 to feedback units), results return in ctx. Reference algorithm script: `config/scripts/hexapod_align.lua` (bobcat XCAN coordinate-descent hill climb — coarse-to-fine step ladder, bidirectional ratchet walk per axis, global-peak recovery; `align_exit_threshold` > 0 = early exit that stops-and-stays the moment any sample reaches target; `align_trace=1` = one `xcan,...` CSV line per sample — seq/time/phase/axis/dir/step/positions/value + deltas vs the previous sample — persisted in the daily log (`logs/firedog_YYYY-MM-DD.log`, newest 30 days kept) for offline algorithm analysis (Trace checkboxes on the Run XCAN band + Scanning tab inject it); results land in ctx as `align_baseline/best/delta/gain/exit_hit`). The "Active align (hexapod)" recipe in `config/recipes.json` shows the injection pattern, and the Motion page's **Scanning tab** is a UI test bench over the same script — a parameter form (device combo, feedback-topic combo listing live DataBus channels, XCAN/Stop, live state + results) that owns no scan logic and injects values via `LuaEngine::Env::initialCtx` (seeded into the run ctx before the script starts, read by `fd.param` exactly like recipe `ctx_set` values). NOTE: bobcat's "Fast Align" is NOT software — it's the PI firmware FSM GCS command; wrapping it as a `pi_fast_scan` C++ command is future work. A failed command raises a Lua error (script `pcall` = its on_error); Stop is honored inside `fd` waits AND by a `lua_sethook` count/line hook (kills pure-Lua loops, reports the executing line to the **Scripts** page, View menu). **Debugger (C3)** on the same hook: click a source row to toggle a line breakpoint (hot-swappable mid-run), Pause/Continue/Step buttons, and the current function's locals shown while paused — the Lua worker blocks inside the hook, so pauses land at line boundaries (a blocking `fd.*` command finishes first); Stop and safety aborts always release a pause. `os`/`io` are not opened. One orchestration owner at a time: `Orchestration::Busy()` keeps the two engines + program runner + path executor mutually exclusive — EVERY Run/Go surface gates on it. sol2/Lua headers never leak out of the .cpp; `SOL_ALL_SAFETIES_ON` is defined. **Cross-calls (C2)**: step execution lives in `command/StepRunner` (shared; `RecipeEngine` is just the worker-thread/status wrapper around it) — `fd.run_recipe(uid_or_name)` runs a recipe synchronously on the Lua worker with the SAME `ExecutionContext` (shared ctx + stop token), and the `run_script` command runs a .lua file inline on the recipe worker via `RunLuaFile` (recursion capped at depth 1: a recipe-spawned script cannot `run_recipe`).
