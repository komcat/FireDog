# Layer 2.5 — commands, recipes & the Lua tier

*The registry that feeds three clients (engine, editor forms, Lua bindings), the
execution model, and the scripted algorithms. Design rationale is split across
`docs/recipe-core-design.md`, `docs/recipe-editor-design.md` and
`docs/lua-tier-design.md`; this is the operational summary.*

## Layer 2.5 — Command layer (`src/command/`)

Design doc: `docs/recipe-core-design.md`. One typed **`CommandRegistry`** (name + `ParamSpec` schema + execute fn capturing `Workflow&`) feeds three clients: the **`RecipeEngine`** (implemented), the recipe editor forms (Phase B), and Lua bindings (Phase C). Recipes are nested-JSON step lists (`config/recipes.local.json` → `recipes.json`, or the product manifest's `recipes` role); control flow (`loop` count/while, `if/else`, `group`, `parallel`, `sub_recipe` cycle-checked, `stop_recipe`) is engine-native — the registry holds only leaf actions. The engine runs ONE worker `std::thread` (dtor stops + joins — no detached threads, ever; a `parallel` block is the one scoped fork-join inside it: one thread per mover lane, all joined before the block returns — see `docs/recipe-core-design.md` §5.2), validates at Start (params, references, devices Connected — recipes never connect hardware), contains exceptions at step boundaries, and aborts on critical safety alerts. **No blocking command may run on the UI thread**; all waits go through `ExecutionContext::Sleep/WaitUntil` (every wait has a timeout) so Stop interrupts within one poll interval. `move_path` requires the device to already be AT `from` (strict start, no nearest-node snapping) and shares `BuildMapRoute` (`core/MotionMap`) with the Motion page's Go button — one planner, two executors (the UI `TickPath` state stays UI-thread-only; the engine drives legs itself). **`manual_adjust`** (bobcat's ManualAdjust, ported v1) pauses the run in a global jog window (NON-modal, kept always-on-top via `BringWindowToDisplayFront` — only the engine worker blocks; the rest of the UI stays usable for camera/jog/click-to-move): the worker blocks in an `awaitAdjust` hook (same handshake shape as the prompt — `ExecutionContext::AdjustRequest`, `AnswerAdjust`, pending state in both engines' Status), while the window jogs via `Workflow::JogGlobal` (step presets = the Jog window's `kSteps`, live positions via `RequestFastPoll`, per-axis enables, STOP, safety-inhibit notice); OK continues (optional `ctx_prefix` records the confirmed position as `<prefix>_<axis>`), Cancel fails the step. Scripts get `fd.manual_adjust{...}` from the generated bindings. The **Recipe Editor** (View menu, full-page like the other editors; design in `docs/recipe-editor-design.md`) is the authoring+run surface: recipe list CRUD, step tree with palette/move/delete, schema-driven forms generated from `ParamSpec` (`DrawParamWidget` — a new command gets a working form for free), shared condition editor, Save to the product recipes file or `config/recipes.local.json`; the executing step highlights via `Status.stepPath`, and the recipe `prompt` window is global (drawn from `DrawMainWindow` like the safety alert; non-modal + always-on-top like `manual_adjust`). `App` owns registry+engines as ONE member — `command/Orchestration.{h,cpp}` (`orch_.registry/recipe/lua/programs`, plus `Busy()` and `StopAll()`) — declared AFTER `workflow_` (destroyed first, like `SafetyWatch`). **Vision commands** live in `CommandsVision.cpp` (category `Vision`): `auto_focus` sweeps one axis, scores each step with the plain-C++ Laplacian-variance measure (`vision/FocusMetric`, no HALCON), waits for provably post-move frames via the camera frame counter rather than a fixed sleep, refines the peak parabolically and writes `autofocus.*` into ctx; `halcon_status` reports the HALCON build/runtime/licence gates into ctx (`require = true` makes it a hard gate) so a recipe can branch on the licence instead of failing halfway; **`vision_detect`** locates a taught feature with a detection model (`ParamType::VisionUid` — resolved by uid or name like `AlignUid`, and NOT device-scoped: a model belongs to the camera) and writes `<prefix>.ok/.x_px/.y_px/.dx_mm/.dy_mm/.angle_deg/.score/.radius_px/.count/.elapsed_ms/.error`, with `require = false` by default so a recipe branches on `.ok` instead of dying; **`vision_test`** runs a model N times and reports hit rate, mean score, per-axis sigma and the worst deviation — what the teach window's Reliability button launches as a one-step ad-hoc recipe. Both need HALCON and report `HalconEngine`'s reason verbatim when it is absent, and both reuse the auto-focus fresh-frame gate; design in `docs/vision-detection-design.md`. All reuse the shared arrival/settle waits in `command/MotionWaits.h` — full detail in `docs/vision-layer.md`. **Align commands** live in `CommandsAlign.cpp` (category `Align`): `align_station` drives to one of a procedure's two stations, applies its exposure/lighting placeholder and captures the marked point (manual = a crosshair pick through the new `awaitPick` hook — same handshake shape as `awaitAdjust`, window in `WndPrompts.cpp`; auto = a taught detection model via `Workflow::Detect`, filling the SAME `PickResult` so everything downstream is identical — and failing loudly, with the licence/miss reason, unless `auto_fallback_manual` asks for the crosshair), `align_solve` builds the rigid 2-D local frame **O1** from E1/E2 and hands it to the UI thread via `Workflow::QueueAlignResult` to persist, and `align_apply`/`move_local` consume it — but only the **LIVE** frame (`Workflow::SetLiveFrame`/`LiveFrame`), never the saved one. A frame describes where ONE physical part sat, so it is session state cleared at program start, DUT open and product load; the persisted copy is a record for the UI, the Aux overlay and traceability. It lives on `Workflow` rather than in `Env` because a program runs each slot as its own engine Start, so per-run state would be wiped between the recipe that aligns and the recipe that works. Design: `docs/alignment-procedure-design.md` §5b. `align_run` is the typed one-step wrapper over `config/scripts/alignment_procedure.lua` (the `xcan` pattern), and the Alignment page's Run button launches the *same* script — so a taught frame can only come into existence one way. It resolves the file through **`ExecutionContext::ResolveScript`**, which normally prefers the PRODUCT's copy of that filename (`ScriptsDir()` = the dir the session actually scanned) over the shipped one — except for the **standard procedures** such as `alignment_procedure.lua` (`IsSystemScript`/`SystemScriptPath`): those always resolve to `config/scripts/`, from the commands and from the two page buttons alike, and a product copy of the name is ignored with a warning (the Scripts page flags it on the file being read). They are edited in step with the commands they call, so a fork silently skips whatever step the app added last. **`xcan_to_target`** (`CommandsSystem.cpp`, category Motion) is a fourth typed wrapper over a standard script, `config/scripts/xcan_to_target.lua`: pass 1 is `fd.xcan` with the coarse ladder, then the fine ladder (`fine_steps_um`) up to `retries` more times, returning on the first pass that reaches `target_ua` (judged on the pass's exit flag or a fresh reading), writing `xcan_reached/passes/best_ua` to ctx and failing the step when none does unless `fail_if_missed` is off; it resolves through `ResolveScript` like `align_run`, because how a scan is retried is not a product's business the way the scan's own parameters are. **`xcan_two_lens`** (`config/scripts/xcan_two_lens.lua`, same deal) is the Run page's "6800 uA / Left Coarse" sequence as a step: left coarse to `target_ua`; short of it, ONE left follow-up picked by the signal (coarse again from `coarse_band_ua`, the fine ladder from `fine_band_ua`, nothing below); still short, ONE right coarse pass; then exit as is, writing `xtl_reached/passes/last/best_ua` and failing only when `fail_if_missed` is on. `run_script`, `xcan`, `raster_scan` and `climb_raster` still take `file` literally — a deliberate omission, since a scan's parameters are a product's business and changing it would re-point products carrying their own script copy. `ParamType::AlignUid` resolves by uid or name and is NOT device-scoped (a procedure carries its own device). Design: `docs/alignment-procedure-design.md`.

**The two-speed move.** Every point-to-point move command — `move_to_position`,
`move_to_position_offset`, `move_relative`, `move_to_position_approach`, `move_lift_off`
(Motion) and `move_local`, `move_to_nominal` (Align) — goes through **one** helper,
`MoveWithApproach` (`command/MotionWaits.h`), which optionally covers the last
`approach_mm` (or `approach_pct` of the distance) at `approach_velocity_mm_s` instead of
arriving at travel speed. With none of the three set it is exactly the plain
`MoveToPosition` → `WaitArrive` → `WaitSettle` it replaced, so no existing recipe
changes. Full contract — the looser travel-leg tolerance, the settle-before-`VLS`
ordering, the velocity restore, and why a half-configured approach FAILS rather than
quietly moving fast — in `docs/pi-hexapod-motion-design.md` §5. The three parameters carry
**`ParamSpec::group = "Approach"`**: the editor folds a *run of consecutive params
sharing a group* under a collapsing header (opened by itself when one is set, or when one
is required — a validation error must never hide behind a fold), which is what keeps
three optional fields off six forms that were already long. `DrawParamWidget` is
untouched and stays one row per `ParamSpec`. The six TOOL approaches (`move_tool_to_camera`,
`move_camera_to_tool`, `move_to_point`, `tool_travel_to_camera`, `grip_move_to_camera`,
`grip_camera_to_object`) share **`ToolVelocityParam()`** (`MotionWaits.h`): the same
`velocity_mm_s`, but defaulting to `kToolVelocityMmS` = 5 mm/s rather than "keep current" — a
registered tool closing on a lens or the camera does not inherit whatever speed the last step
left on the device. A saved step with no value now runs at 5; type 0 to keep current.

**`move_lift_off`** is two legs through that same helper: a short retreat along ONE
local axis (`lift_mm`, default 2; `lift_axis` as `"Z-"` / `"X+"`, empty = by controller
type — a PI hexapod backs off along its own X+, the ACS gantry lifts on Z-), then the
ordinary coordinated move to the saved `position`. The default is decided by
`IMotionController::Type()`, never by the device's name. The approach triple applies to
the ARRIVAL leg only; the lift runs at travel speed on the step's `tol_mm` /
`timeout_ms`. `lift_mm = 0` skips the lift, so the step degrades to `move_to_position`.
It carries `teach` (the destination is what gets taught) and joins `parallel` blocks by
device.

**Tray commands** (`CommandsTray.cpp`, category Tray; design in `docs/waffle-tray-design.md`).
A waffle tray (`core/WaffleTray`, `ParamType::TrayUid` — resolved by uid or name, NOT
device-scoped: the tray carries its device) yields a pose for any cell (row, col) from three
taught corners. **`move_to_cell`** drives there through the same `ApplyPreMove` →
`MoveWithApproach` as the saved-position movers (the two pre-move params and `ApplyPreMove`
now live in `MotionWaits.h` for that reason): `row`/`col` typed, or `row_key`/`col_key` naming
ctx keys (a missing key FAILS — no fallback to the typed value), optional `offset_axis` +
`offset_mm` stand-off (both or neither), `skip_disabled` (a disabled cell otherwise fails),
and it writes `<prefix>_row/_col/_moved`. It is not a teach mover (no `teach` param — a cell
has no position row to write into) and not a parallel mover (no `parallelBy` — its device is
inside the record). **`move_to_active_cell`** is the same move to the tray's ACTIVE cell
(`Workflow::TrayActive`: clicked on the grid, or the last `tray_next`), failing when none is
set; both movers take `mark_used` (default off — arriving is not taking). **`tray_mark_used`**
is the step after the work in a run-per-part recipe: it marks the active cell used and makes
the next full cell after it (in `order`) the active one, so the next run carries on there.
**`tray_next`** takes the next enabled cell that still holds a part
(`row_major` / `col_major` / `serpentine`; `wrap`), marks it USED and writes
`<prefix>_row/_col/_index/_remaining/_ok`, `_ok = false` when the tray is empty (Success
unless `require`); **`tray_reset`** marks every cell full. Used cells are PRODUCT state
saved with the tray (`usedCells`); the worker reads and marks the live cursor on `Workflow`
and queues the change (`QueueTrayUsed` → `TakeTrayUsed`, drained in `App::Update` into
`ProductSession::SetTrayCellsUsed`), so a restart carries on at the next full cavity. The
cursor is re-seeded at product load and NOT cleared at program start, so a program takes
one cell per part. The `loop` step's optional **`index_ctx`** writes the 1-based pass number of a
`count` loop into ctx before each pass, which is how nested loops drive `row_key`/`col_key`.

**Lua tier** (`command/LuaEngine.{h,cpp}`, design in `docs/lua-tier-design.md`): plain `.lua` programs (product `scripts/` dir, else `config/scripts/`; edited on the **Scripts page** — syntax colour, completion from the registry, a compile-only syntax check, lint of `fd.*` names, Save/Revert/New with the Recipe Editor's dirty guard; design-doc item C4 — or in any external editor, since the engine always runs the FILE and Run is disabled while the buffer is dirty) run through bindings **generated from the same registry** — `fd.<command>{named=args}` validated by the same `ParamSpec` schemas, plus `fd.read/ctx/sleep/log/logf/prompt/input/positions/clock` and `fd.param(name, default)` — the recipe→script parameter-injection convention: recipes set ctx keys (`ctx_set` steps, typically grouped as "<algo> parameters") before `run_script`, the script reads them with defaults and logs each resolved value. Sibling algorithm script `config/scripts/raster_scan.lua` (bobcat GridScan port): serpentine area scan for first-light search — slow axis one-sided from start (`raster_slow_dir`, default X−), fast axis centered ±half-span (default Y), absolute grid targets off the start pose, same fresh-sample measure + exit-threshold stop-and-stay as the align script, returns to the best node otherwise; signal-gated cycle cuts: row-peak early stop (rows past the spot are dark) and fast-axis tracking (next row sweeps a narrow window around the previous row's peak) (`raster_*` params/ctx results, `rast,` trace lines). Third algorithm script `config/scripts/climb_raster.lua` (Horizon `RasterClimbEngine` port, design in `docs/climb-raster-design.md`): the gap-closing search that runs BETWEEN raster and XCAN — step the climb axis toward the part, probe once where the stage already stands, and search the XY plane (cross line-scan or square spiral) only when the step alone stops paying; stops on the target fraction, on a plane best collapsing below the peak (suspected contact — retreats to the peak), or on the travel budget, and parks on the run's best point on EVERY exit including an error (`climb_*` params/ctx results, `clmb,` trace lines). Its `climb_target` is mandatory: unlike a grid or a ladder this search has no intrinsic budget, so the target is what ends it. All three scripts also front as typed leaf commands (`xcan`, `raster_scan`, `climb_raster`, category Motion, in `CommandsSystem.cpp`): the step form's params are injected as the script's ctx keys (other `align_*`/`raster_*` keys ctx_set beforehand still pass through `fd.param`), then the file runs inline via `RunLuaFile` — exit targets are entered in **uA** (×1e-6 to feedback units), results return in ctx. Reference algorithm script: `config/scripts/hexapod_align.lua` (bobcat XCAN coordinate-descent hill climb — coarse-to-fine step ladder, bidirectional ratchet walk per axis, global-peak recovery; `align_exit_threshold` > 0 = early exit that stops-and-stays the moment any sample reaches target; `align_trace=1` = one `xcan,...` CSV line per sample — seq/time/phase/axis/dir/step/positions/value + deltas vs the previous sample — persisted in the daily log (`logs/firedog_YYYY-MM-DD.log`, newest 30 days kept) for offline algorithm analysis (Trace checkboxes on the Run XCAN band + Scanning tab inject it); results land in ctx as `align_baseline/best/delta/gain/exit_hit`). The "Active align (hexapod)" recipe in `config/recipes.json` shows the injection pattern, and the Motion page's **Scanning tab** is a UI test bench over the same script — a parameter form (device combo, feedback-topic combo listing live DataBus channels, XCAN/Stop, live state + results) that owns no scan logic and injects values via `LuaEngine::Env::initialCtx` (seeded into the run ctx before the script starts, read by `fd.param` exactly like recipe `ctx_set` values). NOTE: bobcat's "Fast Align" is NOT software — it's the PI firmware FSM GCS command; wrapping it as a `pi_fast_scan` C++ command is future work. A failed command raises a Lua error (script `pcall` = its on_error); Stop is honored inside `fd` waits AND by a `lua_sethook` count/line hook (kills pure-Lua loops, reports the executing line to the **Scripts** page, View menu). **Debugger (C3)** on the same hook: click a source row to toggle a line breakpoint (hot-swappable mid-run), Pause/Continue/Step buttons, and the current function's locals shown while paused — the Lua worker blocks inside the hook, so pauses land at line boundaries (a blocking `fd.*` command finishes first); Stop and safety aborts always release a pause. `os`/`io` are not opened. One orchestration owner at a time: `Orchestration::Busy()` keeps the two engines + program runner + path executor mutually exclusive — EVERY Run/Go surface gates on it. sol2/Lua headers never leak out of the .cpp; `SOL_ALL_SAFETIES_ON` is defined. **Cross-calls (C2)**: step execution lives in `command/StepRunner` (shared; `RecipeEngine` is just the worker-thread/status wrapper around it) — `fd.run_recipe(uid_or_name)` runs a recipe synchronously on the Lua worker with the SAME `ExecutionContext` (shared ctx + stop token), and the `run_script` command runs a .lua file inline on the recipe worker via `RunLuaFile` (recursion capped at depth 1: a recipe-spawned script cannot `run_recipe`).
