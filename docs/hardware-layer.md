# Layer 1 — hardware drivers

*Per-device reference: SDK calls, threading, and the behaviours that were ported
deliberately from `bobcat_engine`. Read the entry for a device before touching
its driver — several of these encode hardware quirks that cost real debugging
time (the 6482 `:READ?` note especially).*

## Layer 1 — Hardware

**Truth source:** all hardware-connection code is ported from **`bobcat_engine`** (the battle-ready production controller), NOT BobDog. When adding a module, read the matching adapter in `..\komcat\bobcat_engine\include\` and port its actual SDK calls, dropping the Qt/abstraction layers.

Two driver shapes coexist, both PIMPL (vendor headers never leak into ours), both with a same-API simulated stub when the SDK compile def is absent:
- **Direct-SDK singletons** (camera, CLD101x, PD3 lighting) — one concrete class, no interface.
- **The PSU fleet** (UDP3305S) — one concrete class, but EVERY enabled `udp3305` entry is built, each in a `HardwareManager` slot (`AddPsuSlot`, `PsuDevice/PsuState/PsuName(i)`, `PsuIndex(name)`) like the IO fleet. A slot outlives its driver: a reconnect rebuilds the driver in place, so the index and the `ConnState` atomic never move. Everything above layer 1 names a supply by its config `name`, and **`""` means the first** — so a `psu_*` step saved before there were several still drives the supply it always drove. Each publishes `psu/<name>/ch<n>/v|i`; the FIRST also keeps the device-less `psu/ch<n>/v|i`, because saved readouts and charts reference those names.
- **Fleets behind an interface** (`IMotionController` for PI/ACS, `IIoDevice` for Ezi-IO/WAGO, `ISmu` for the 6482/2602B) — multiple heterogeneous devices; Workflow builds each from config and hands it to `HardwareManager` (`AddMotion`/`AddIo`/`SetKeithley`), which stores it in a slot with its own `ConnState` atomic (slots held by `unique_ptr` so the atomics stay put). The SMU is a fleet of exactly one: `HardwareManager` holds a single `unique_ptr<ISmu>` and `Workflow::LaunchKeithleyConnect` is the ONE place a concrete meter is chosen.

Modules:
- **Camera** — `hardware/camera/PylonCamera.{h,cpp}`. Direct Pylon SDK. Ported from bobcat_engine: GigE heartbeat + max packet size, `GrabStrategy_LatestImageOnly` + `GrabLoop_ProvidedByUser`, a grab thread, `CImageFormatConverter` → RGB8, mutex-guarded latest frame. Exposure control via SFNC `ExposureTime` (legacy `ExposureTimeAbs` fallback), `ExposureAuto` forced Off at connect; `GetInfo()` snapshots identity + measured fps. The UI pulls frames via `App::UpdateCameraTexture` (shared texture; fresh-frame gated, so Aux + Camera page can both draw it). The **Camera page** drives connect/disconnect/exposure through `Workflow` (`ConnectCamera`/`DisconnectCamera`/`SetCameraExposure`; the config is captured at `Start` for reconnects) and edits the pixel→mm calibration live, saved back into the camera's `hardware.json` entry via `HardwareConfig::SaveCameraSettings` (read-modify-write; `exposure_us` is also applied after every connect).
- **Keithley 6482** — `hardware/instruments/Keithley6482.{h,cpp}`. Direct VISA. SCPI from bobcat_engine's `Keithley6482Adapter`: `*IDN?`, `*RST`/`*CLS`, `:SYST:ZCH OFF`, `:FORM:ELEM CURR1,CURR2` (dual read), NPLC + range, `:SOUR:VOLT`/`:OUTP ON` bias, `:READ?` parse. A `std::thread` poll loop publishes both channels to the DataBus; `Workflow::Start` connects it async and applies the config's **`bias_voltage`** (default 1 V) to ch1. Runtime setters (`SetNplc`, `SetRangeAuto/Fixed`, `SetVoltageBias`, `OutputOff`) issue SCPI under the same `visaMutex` the poll loop's `:READ?` holds, so they're safe while measuring; bias/output commands are **verified against the instrument** (`:OUTP?` read-back, like bobcat's `IsOutputOn`) and the SCPI error queue (`:SYST:ERR?`) is drained into the log so silent rejections surface; `GetConfig()`/`BiasVolts()`/`OutputOn()` are cheap UI reads off a separate `cfgMutex`/atomics that never block on VISA. The **Keithley page** drives connect/disconnect + all runtime settings through `Workflow` (`ConnectKeithley`, `SetKeithleyNplc`, `SetKeithleyPollInterval` = polling restart, …; config captured at `Start` for reconnects) and saves them back via `HardwareConfig::SaveKeithleySettings`. The chart pipeline is shared: `UpdateKeithleyChartData` (once per frame from `App::Update`) fills the buffers, `DrawKeithleyChart` renders in both the Aux overlay and the page.
  - **Sample rate** is governed by `measurement_nplc` (integration time), not the poll interval: NPLC 0.1 ≈ 80 Hz, NPLC 1 ≈ 30 Hz, NPLC 5 ≈ 12 Hz. `poll_interval_ms: 0` means "as fast as the instrument allows". The poll loop reads with **`:READ?`** each iteration (INIT+FETCh in one transaction) — the proven 6482 method (see `komcat/komcat_CMakeProject2/serverPython/Keithley6482/hardware/smart_multimeter.py`). Do **not** configure `:INIT:CONT ON` or read with `:FETC?`: on the 6482 continuous-init makes every `:READ?` raise -213 "Init ignored" and the stream stalls at 0 Hz. Don't add a fixed inter-read sleep either.
- **Keithley 2602B** — `hardware/instruments/Keithley2602B.{h,cpp}`. The other `ISmu`, and the first **TSP** instrument in the build: the 2600B series has no SCPI mode, so every line sent is Lua run on the instrument (`smua.measure.nplc = 0.1`) and a "query" is `print(<expr>)`. Direct VISA over **LAN** — `TCPIP0::<ip>::INSTR` (VXI-11) or `TCPIP0::<ip>::5025::SOCKET`; the driver enables the `'\n'` termchar, which is what ends a read on a raw socket. `localnode.prompts = 0` and `localnode.showerrors = 0` go out **before the first query**, or `TSP>` tokens interleave and every read comes back one reply out of step. One `print(string.format("%.6e,%.6e", smua.measure.i(), smub.measure.i()))` per poll returns both channels in one round trip, parsed by the same `ParseDual` as the 6482. Setpoint/settings changes are read back (`print(smuX.source.output)`, `print(smuX.measure.rangei)`) and `errorqueue` is drained into the log after every runtime setter.
  - **It is a SOURCE-measure unit, and that is the one behavioural difference.** A 6482 measures with its voltage source off; an SMU reads ~0 A with its output off — indistinguishable on the chart from a dark photodiode. So `SetVoltageBias` switches **every enabled channel ON** (ch1 at the bias, ch2 at 0 V) and `OutputOff` drops them all; `OutputOn()` is true only when every enabled channel reads back on.
  - **NPLC is 0.001..25** here (narrower than the 6482) and out-of-window values are silently ignored by the instrument, so `SetNplc` clamps and stores the clamped value. The UI's fixed-range table holds the 6482's decades (2 nA..20 mA) but the 2602B's floor is 100 nA — it selects the smallest range containing the request, so `SetRangeFixed` reads `smuX.measure.rangei` back and stores what was actually chosen. Full detail: `docs/keithley-polling-design.md` §6.
- **CLD101x** — `hardware/instruments/CLD101x.{h,cpp}`. Direct VISA (USB, `USB0::0x1313::0x804F::<serial>::INSTR`), ported from bobcat_engine's `CLD101xDirectAdapter`: lowercase Thorlabs SCPI (`source1:current:level:amplitude` in **amps** — the API takes **mA**; `source2:temperature:spoint`; `output1|2:state on/off`; `SENSe2:temperature:data?` / `sense3:current:dc:data?`), `viWrite/viRead` with `\n` termchar, 2 s I/O timeout, 200 ms USB settle after open. On/off commands are read-back verified (`output1|2:state?`). A 500 ms poll thread caches a `Status` snapshot and publishes `cld/temp` (°C) + `cld/current` (mA). **Nothing is written to the outputs at connect or disconnect** (bobcat behavior — device state persists; laser ON is always an explicit UI action, and there are no interlocks in the device layer). Config defaults (`default_temperature`/`default_laser_current`) only seed the UI; the **CLD page** drives everything through `Workflow` (`ConnectCld`, `CldTecOn/Off`, `CldLaserOn/Off`, `SetCldTemperature`, `SetCldLaserCurrentMA`) and saves defaults via `SaveCldSettings`.
- **UDP3305S** — `hardware/instruments/UDP3305S.{h,cpp}`. Direct VISA (USB, `USB0::0x0483::0x5740::<serial>::INSTR` — UNI-T enumerates with the STMicro VID), ported from bobcat_engine's `UnitTUDP3305S`: 3 channels (CH1/CH2 0–32 V / 0–5 A, CH3 0–6 V / 0–3 A). Setpoints use the hardware-verified `APPLy CH<n>,<v>,<i>` form with `SOURce<n>:VOLTage?/:CURRent?` read-back; output switches (`OUTPut CH<n>,ON|OFF`) are read-back verified via `OUTPut? CH<n>`. A 500 ms poll thread reads `MEASure:VOLTage?/:CURRent?` per channel (plus output state, so front-panel changes surface) and publishes `psu/ch<n>/v|i`. **Nothing is written at connect**, but **disconnect forces every output OFF** — bobcat's PSU safety habit, deliberately different from the CLD. The **PSU page** drives everything through `Workflow` (`ConnectPsu`, `SetPsuVI`, `PsuOutputOn/Off`); the config carries only identity + polling (setpoint edits seed from the device at connect — nothing to save back).
  - **CV / CC.** The supply has **no mode switch**: it holds the voltage setpoint until the load wants more than the current limit, then holds the limit — the load decides. So a "mode" is only which number is the TARGET and which the LIMIT, and which reading is checked. `UDP3305S::IsCurrentLimited` (output ON and I ≥ 98 % of the limit) is the one definition of "it is in CC". The page has a CV/CC choice per channel (default CV; it relabels the fields and colours the live `[CV]`/`[CC]` tag orange when the load disagrees) and never sends anything for it.
  - **Quick access:** the Jog window's **PSU** tab is a supply picker plus the page's own channel controls (`App::DrawPsuChannelControls`, compact) — one selection (`psuSel_`), one set of edits, one apply path, held to the PSU page's role. Connect/disconnect stays on the page.
  - **`Measure(ch, v, i, on)`** reads a channel NOW under the VISA lock (not the poll cache, up to 500 ms old) — what `psu_startup` verifies against. The simulated stub is a 100 Ω load, so it shows CV and CC.
- **CCS PD3 lighting** — `hardware/lighting/CcsPd3.{h,cpp}`. The PD3-10024-8-EI LED controller on the LAN (192.168.0.2:40001), ported from Horizon's `CcsPd3Adapter` (hardware-verified; CCS guide KZ03995 §8). **Raw Winsock, no SDK, so no `HAS_*` gate**; `"simulated": true` swaps the socket for an in-memory controller that answers the SAME frames, so framing, checksums and reply parsing run either way.
  - **Protocol.** `@` + 2-digit wire channel + command + data + checksum (low byte of the ASCII sum from `@`, two uppercase hex) + CRLF. Replies `@ccO<data>ss` (accepted) or `@ccN<ee>ss` (01 command, 02 checksum, 03 range); the reply's checksum and channel echo are both checked. Used: `Fnnn` intensity 0..255, `L0`/`L1` output, `M` status `F075.S04.L0`, `C` unit check (`11` = overcurrent/fan stop). **Channels are front-panel numbers (L1 = 1) everywhere above the driver; the wire's 0-based code exists only inside it.**
  - **One TCP client, graceful close.** The PD3 has a single client slot. The link is held open, and closed by half-close + bounded drain until the peer closes — an abortive close can leave the slot busy until the controller is power-cycled. Connect is bounded (non-blocking `connect` + `select`, 3 s) and its failure text says another program may hold the slot. While Horizon or the CCS utility is connected, FireDog cannot be.
  - **0 % is OFF.** `F000` still glows ~0.4 % on 24 V units, so intensity 0 sends `L0` then `F000`; anything else `Fnnn` then `L1`.
  - **Failure split.** A rejected command (NG) keeps the link. Any I/O error, timeout or malformed reply drops it — the stream is out of step — and the poll thread reopens it on its next tick (the WAGO pattern), so a pulled cable recovers on its own. `ConnState` stays Connected through that (it means "a session the operator opened"); `Status::linkUp` is the live truth and the page shows it.
  - **Threads.** One poll thread (C + M per channel every `poll_interval_ms`, default 1000) publishes `light/ch<n>/pct` and `light/ch<n>/on`; a channel in strobe mode is reported as a warning (it is dark without a trigger). Blocking setters (`SetIntensity`, `SetIntensities` — a whole call-out under one lock) are for workers; **`Request()` is the UI's**: it queues the latest value per channel and wakes the poll thread, which sends it, so no slider ever puts a TCP exchange on the UI thread.
  - **Lights and call-outs.** `hardware.json` gives each channel a `color` and a `group`; a LIGHT is a group (or an ungrouped channel's name). `core/LightCallout` is the one matcher: `red|green|blue|collimate` light the matching channels, `white` = R+G+B, `white_collimate` = both, and every other channel of that light goes to 0. `Workflow::LightTargets` resolves a call-out from the config captured at Start and refuses one that would light nothing. **Nothing is written at connect or disconnect** — the lights stay as they are.
  - The **Light page** (Hardware → Lighting, Technician) drives it through `Workflow` (`ConnectLight`, `RequestLightCallout`, `RequestLightChannel`); its sliders follow the read-back whenever they are not being dragged, and editing locks while `orch_.Busy()`. Recipes: `light_set`, `light_color`, `light_off`, `light_read`. Detection models (not stations) carry an `AlignLighting` (kind `light`) — see `docs/vision-detection-design.md`.
- **Motion** — `hardware/motion/`: `IMotionController` + `PIHexapod` (GCS2) and `ACSController` (ACSC over TCP). Poll threads publish per-axis positions to `motion/<device>/<axis>` and use **adaptive polling**: `RequestFastPoll()` is a demand signal — consumers that need realtime positions (open motion page, active procedure) call it repeatedly; the driver polls fast for a short window and drops to a slow idle rate otherwise. **Per-axis servo enable** is an optional capability (`SupportsAxisEnable`/`AxisEnabled`/`SetAxisEnabled`, default off): ACS implements it with `acsc_Enable`/`acsc_Disable` and reads the `ACSC_MST_ENABLE` bit of `acsc_GetMotorState` in the same poll as the positions, so the Motion page's ON/OFF indicator shows what the controller reports, not what was last asked. The simulated ACS refuses a move on a disabled axis, as the controller does. The UI reaches it only through `Workflow::SetAxisEnabled` (refuses an enable while the safety alert stands; a disable ends a running path on that device), behind the jog arm and `orch_.Busy()`.
- **Digital IO** — `hardware/io/`: `IIoDevice` + `EziIoDevice` (FAS lib) and `WagoIoDevice` (Modbus TCP; `simulated: true` gives an in-memory sim with no sockets). **Pin addressing is normalized: bit i == pin i for BOTH inputs and outputs** — any vendor bit layout (EZI-IO packs outputs at bits 8+/16+) is translated inside the driver; a shifted value must never cross the interface. Latch semantics differ: EZI-IO latches input edges in hardware; WAGO synthesizes rising edges in software per poll cycle (misses pulses shorter than the interval). Pins have config names, resolvable both ways (`InputPinByName` etc.) — pneumatic slides, IO watch, and safety watch all reference pins **by name**, resolved once at startup by Workflow.
- **Pneumatic slides** — `hardware/pneumatic/PneumaticSlide.{h,cpp}`. Synthetic devices composed from IO pins (one output = extend, two position sensors). The core is **passive**: `Update()` advances the state machine from the IO drivers' cached `Status()` (never hardware), and Workflow ticks it every frame. No `ConnState` — a slide's "connection" is its underlying IO devices. `ExtendAndWait`/`RetractAndWait` block — never call from the UI thread.
- **IoWatch** — `hardware/io/IoWatch.{h,cpp}`. Background thread mapping input edges to output actions (toggle / set_on / set_off / momentary) with per-binding debounce. A binding may name an optional **`indicator`** output (a switch's LED) that the watch thread drives to the bound output's level every tick, read from the output device's cached `Status()`. It therefore shows the output's state whoever set it (the switch, the IO page, a recipe), corrects an LED flipped by hand within one tick, keeps following while "Watch bindings" is paused, writes only on a difference, and is left alone while either device has no valid status. An unresolved indicator drops only the LED, never the binding. Editable at runtime via the IO Watch editor window; `Workflow::ApplyIoWatch` swaps the running watch.
- **SafetyWatch** — `hardware/io/SafetyWatch.{h,cpp}`. First-priority: polls safety inputs (E-Stop etc.), latches ONE alert until acknowledged, fires a callback from the watch thread. For **critical** signals Workflow's callback calls `StopAllMotion()` immediately, and new motion commands are blocked (`SafetyBlocked()`) until the UI's modal alert is acknowledged.
- `IDevice` / `SimulatedDevice` — the generic simulated placeholder; nothing real uses it now that the SMU is ported.
