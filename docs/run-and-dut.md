# Programs, the Run page & DUT traceability

*How an operator run is assembled and executed, and how results are recorded
against a part. Design docs: `docs/run-page-design.md`, `docs/dut-design.md`.*

## Programs + Run page (`command/Program`, `command/ProgramRunner`, design in `docs/run-page-design.md`)

A **program** = ordered slots, each an ordered list of recipe **uids** (rename-safe); program uid minted at creation = the traceability identity. Persistence fills the manifest's `programs` role (`SaveProduct` writes it; `config/programs.local.json` fallback). Execution: **no new engine** — `ProgramRunner` (App-owned, ticked from `App::Update`, UI-thread only) sequences ordinary `RecipeEngine` runs from ONE resolved queue serving two granularities (`RunScope::Slot|Recipe` — there is deliberately no whole-program scope: a multi-slot program is a station sequence an operator walks, and `BuildRunQueue` enforces that, not just the UI), so each recipe keeps its own validation, progress, prompts, and `$run` DUT event; the deck selection → queue resolution is `BuildRunQueue` (`command/ProgramRunner`, NOT the UI — a recipe uid missing from the library fails the whole request rather than being skipped); slot runs add a `$run {kind, name, uid, result, recipes_done}` (`DutSession::RecordRun` extension). Stop marks the queue dead then `RequestStop()`s the engine — propagates through command waits and Lua sub-runs. The **Run page** (View menu, full-page): deck (active-slot combo showing ONE slot and its recipes, missing uids red, running item gold, light editing behind the strip's Edit toggle with Save*/dirty; the (program, slot) pair persists by program UID in `UiSettings run_prog_uid`/`run_slot` and is re-applied on every product load that still has it), middle column stacking the execution view (queue with per-item marks + recipe progress), a **Scan band** — one shared header (DataBus feedback-channel picker with live value, three exit-target slots in µA: left-click activates, right-click edits in a modal, the active slot injects the scripts' exit threshold ×1e-6, plus the Trace checkbox) over two tabs: **Raster** (span/step knobs + per-hexapod Scan launching `raster_scan.lua`) and **XCAN** (bobcat Run-page scan controls: hex-left/hex-right × Coarse `10,5,2,1`µm / Fine `2,1,0.5`µm presets launching `hexapod_align.lua` via `StartXcanPreset` with script defaults otherwise, Stop, inline align results), and a **log band** (the shared `DrawLogPanel`), DUT panel (shared `DrawDutBlock`), and a top run strip carrying one **Execute** button whose granularity follows the deck selection (recipe if one is selected, else the shown slot — a label beside it shows which) and which toggles to **Stop** while running, plus **Save**, a **Load** button opening the program list as a modal (no program combo in the deck), the loaded program's name and the **Edit** toggle; right-clicking a deck recipe opens it in the Recipe Editor (Close returns to Run). Failure policy v1: any recipe failure stops the run loudly. Ctx does NOT flow between recipes — cross-recipe data goes through the DUT or DataBus. The strip also carries the **Teach** toggle (Motion-page level, disabled while busy, never persisted, cleared at sign-out): while on, every Run/Execute is a **teach run** — the recipe is rewritten to its moves to saved positions (`command/TeachMode.h`), each arrival opens Manual Adjust with **Save position / Skip**, and Save writes the live pose into that position by uid; a teach run sets no deck mark, does not advance the cycle and writes no `$run` (design: `docs/recipe-core-design.md` §6.1).

## DUT traceability (`core/DutSession`, design in `docs/dut-design.md`)

One active DUT (part being produced/tested) process-wide, identity = (product, serial); thread-safe singleton like DataBus. Storage: `products/<name>/data/<serial>/dut.json` (+ `images/` reserved) — an append-only entry log `{seq, t, key, type, value}` flushed after EVERY mutation via write-temp-then-rename; **a loaded product is required** (App wires `SetProduct` on load/switch, which auto-closes the active DUT). Lifecycle: Open = load-or-create (destructive fresh record only via `new=true`), auto-close-on-new validates the NEW identity first; Close stamps `closed_at` + optional pass/fail. Engines auto-append a `$run` event (kind/name/result) at every run's terminal state — soft no-op with no DUT open (the ONLY soft path; inserts fail hard). Commands: `dut_open` (serial param or ctx key `serial`), `dut_close`, `dut_set`, `dut_record` (ctx→DUT), `dut_record_all`, plus `prompt_input` (text/barcode modal into a ctx key — Enter submits). Lua reads via `fd.dut.serial()/product()/is_open()` and `fd.input(msg)`. UI: DUT block on the Overview left panel (serial entry + Open, Pass/Fail/Close, and a "Data" button that opens the DUT's record folder — or the product `data/` root — in Explorer via `DutSession::BrowseDir`), active serial shown in both run strips; **DUT Records** viewer page (View menu, read-only: serials / entry table / run history); **View Data** window (View menu, Technician, read-only: every record of the product as one table — a row per serial, a column per non-`$` key holding the LAST value written under it — sortable by any column, serial filter, time presets (this month / last month / year to date, by the UTC `opened_at` prefix), plus a chart of one or two chosen keys — a series across the parts in table order with vertical serial labels, or daily / weekly (Monday-named) / monthly box plots (min / Q1 / median / Q3 / max) for when a series is too crowded to read; Double-click or Details jumps to that serial in DUT Records. It rescans on open, on product change and on Reload, never per frame). `dut_capture_image` saves the latest camera frame as PNG (stb_image_write, fetched via FetchContent) into the record's `images/` with a linked `type="image"` entry. `$`-prefixed keys are reserved for events.
