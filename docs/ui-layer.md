# Layer 3 — UI

*Host, theming, fonts, page structure and the interaction rules. For WHERE a
given piece of UI code belongs, see `docs/ui-file-layout.md` — this file covers
everything else about the UI layer.*

## Layer 3 — UI notes
- **File layout — read `docs/ui-file-layout.md` before adding a page, window, or shared widget.** `src/App.cpp` is a ~240-line **composition root** (`Run()`, `Update()`, `SwitchPage`, the ProductSession wrappers); every `Draw*` function is still an `App` member declared in `App.h` but **defined out of line** in a per-surface TU under `src/ui/pages/` or `src/ui/windows/` — the same multi-TU-one-unit shape as `command/Commands*.cpp`. No context structs, no friends. Rules: **page state stays an `App` member** (new file-scope *mutable* state in a page TU is a bug — UiSettings persistence and cross-page sharing both read App members; `constexpr` tables and anon-namespace helpers are fine); a helper lives in the file that uses it, and only moves to **`ui/Widgets.{h,cpp}`** when a second TU needs it (`StateColor`/`Glyph`/`Text`, `DeviceStatusLine`, `Splitter`, `FormatCurrent`, `MeasuredHz`, `KeiRangeIndexFor`, the `kFonts`/`kSteps`/`kKeiRanges`/`kUiSettingsPath` tables). **`Widgets.cpp` is the only UI TU that includes `windows.h`** (it backs `OpenFolderInExplorer`) and **`WndPrompts.cpp` the only one that includes `imgui_internal.h`** (`BringWindowToDisplayFront`) — keep both that way. When moving code between these files keep window/child/label strings and call order byte-identical (ImGui IDs derive from the runtime stack, not source location) and never mix a move with an improvement in one commit. CMake needs no edits — `GLOB_RECURSE … CONFIGURE_DEPENDS`.
- **`Theme`** (`src/ui/Theme.{h,cpp}`) — centralized ImGui styling as a table of selectable themes (FireDog Dark / Deep Blue / Graphite / Light). `Theme::Apply(index)` rebuilds the style from a fresh baseline (preserving `FontSizeBase`, which GlHost owns) and re-derives ImPlot's auto colors; the Display header's theme combo hot-switches it and the index persists in `UiSettings`. Every theme keeps `WindowRounding = 0` (multi-viewport OS windows) — put all global style/color tweaks here rather than scattering them across panels.
- **`GlHost`** (`src/ui/GlHost.h`) is our own thin host over GLFW + OpenGL3 + Dear ImGui. It owns the main OS window, the GL context, and the ImGui/ImPlot lifecycle. `Init` enables **both** `DockingEnable` and `ViewportsEnable` (multi-viewport = real extra OS windows). `EndFrame` renders the main window, then `UpdatePlatformWindows()/RenderPlatformWindowsDefault()` for detached viewport windows, restoring the GL context after. It exposes `MakeTextureRGBA()` (GL 3.0, via `opengl32`) so we don't depend on raylib for textures.
- **Fonts** — `GlHost::SetFont(ttfPath, sizePx)` / `SetFontSize(sizePx)` change the UI typeface/size (ImGui **1.92 dynamic fonts** — the backend owns the atlas texture via `ImGuiBackendFlags_RendererHasTextures`, so there is **no** `Create/DestroyFontsTexture`). Changes are **deferred to the next `BeginFrame`** (safe to call mid-draw): size is just `style.FontSizeBase`, and the atlas is only reloaded when the *typeface path* actually changes. A missing/bad path falls back to the built-in scalable font. Default is **Segoe UI 26 px**; the Display header offers a picker (`kFonts` table in `ui/Widgets.h`), persisted via `UiSettings`.
- **Main window** is paged (`Page` enum, Hardware menu): **Overview** (status + vision + log), **Camera** (connect/disconnect / exposure + pixel→mm calibration + preview / identity + stream info), **Keithley** (connect/disconnect / bias + NPLC/range/poll live tuning + chart / identity + live values), **CLD101x** (connect/disconnect / TEC + laser setpoints and on/off / identity + live values), **Motion** (PI + ACS: device list / tabbed detail — **Positions** table + **Mapped Path** graph editor (drag nodes, Edge mode links clicked nodes, right-click adds/deletes, From→To Go runs the path executor) + **Scanning** XCAN test bench / live axes), **IO** (device list / output toggles / live inputs), **Pneumatic** (slide list / Extend-Retract-Stop / sensor states). Every page uses the same three-panel layout (left list, middle detail, right live info) with draggable splitters whose pixel sizes persist in `UiSettings` and are shared across pages. Global F-key shortcuts activate pages: **F1** Run, **F2** Recipe Editor, **F3** Motion, **F4** Scripts (never with Alt — that is the OS close request), **F5** Alignment, **F6** Placement; a quick-access button strip under the menu bar offers the same six and highlights the current page. They **activate**, never toggle, so the key for the page you are on does nothing. F6 is the one that carries a subject: Placement opens on the procedure the Alignment page has selected, so it is disabled (and logs a warning from the key) with none selected, and re-opening an already-open Placement page is suppressed because that would reset its marks. ALL page switches route through `App::SwitchPage` (`ToggleEditorPage` wraps it for the menu toggles): it owns the takeover/prevPage bookkeeping AND the dirty-recipe guard — leaving the Recipe Editor with unsaved edits blocks on the editor's Save/Discard/Cancel modal, which completes the deferred switch to `edLeaveTarget_`. Don't assign `currentPage_` directly — a caller with custom prevPage semantics (the Run deck's right-click shortcut) sets `prevPage_` itself and *then* calls `SwitchPage`. **A run outranks navigation.** While `orch_.Busy()` the dirty-recipe guard is skipped and the switch goes straight through: the guard is an ImGui *modal*, and a modal blocks input to every other window — including the always-on-top prompt / `manual_adjust` / align-pick windows an engine worker is blocked on. Raised mid-run it leaves the operator looking at a prompt they cannot click while the machine waits, and the run dies on the Stop that follows. The edits are not lost: they stay in memory, still dirty, and the guard fires the next time the machine is idle. Same rule inside the Recipe Editor itself — its editing surfaces gate on `orch_.Busy()` (not `recipe.Running()`, which blinks false between a program's queue items), Step and Next are disabled while `programs.Active()` because they would pause somebody else's run, and its Stop stops the *program* rather than one recipe out of the queue. The **IO Watch editor** and **Transforms editor** (View menu) are full-page takeovers of the main window — they replace the panel layout until their top-right Close button returns to the previous page (`prevPage_`); each edits a working copy (watch: Apply rebuilds the live watch, Save also writes `config/hardware.json`; transforms: edits hot-apply, Save writes `config/motion_transforms.json`). The **Alignment page** (View menu) is a takeover in the same family: procedure list (New/Duplicate/Delete/Save, dirty marker) | the two station cards (saved-position combo + Go + **Teach here** — which captures the current pose as a position private to the procedure: `algn_<procUid>_<n>`, `hidden`, dropped when the procedure is deleted — plus exposure, the lighting placeholder, Manual/Auto) with the **Run alignment** button | the taught frame (E1/E2, origin, θ, span, and a local→machine calculator whose **Move here** button drives to the computed XY behind the shared `jogArmed_` arming flag). Run launches `alignment_procedure.lua` through the Lua engine — the page never captures a point itself; the crosshair pick surfaces in the global `DrawAlignPickWindow` (`WndPrompts.cpp`) exactly as it would for a recipe's `align_run` step. See `docs/alignment-procedure-design.md`. Separate windows: **Jog** (View menu; two tabs — **Jog**: the motion fleet, armed via checkbox, W/D·A/S·R/F keys; **Camera**: the camera fleet — device combo, the Camera page's exposure controls (shared via `DrawCameraExposureControls`), the live focus score + ROI combo, and the **Autofocus Z−** button, which runs the `auto_focus` command as a one-step ad-hoc recipe on the engine worker, gated on `jogArmed_` + `orch_.Busy()` — see `docs/vision-layer.md`), the blocking **safety alert modal**, and the **Aux window** — camera image + Keithley ImPlot chart, positioned outside the main viewport on first use so multi-viewport spawns it as its own OS window (drag to a second monitor).
- **Dangerous actions are gated**: IO output toggles and pneumatic commands sit behind an armed checkbox (default ON as a kill switch); jog and Aux click-to-move (image click → `MoveGantryRelativeMM` via the `pixelToMm` calibration) default OFF and must be explicitly armed. The Aux window's cursor crosshair + dX/dY readout only draw while click-to-move is armed (they describe the move a click would command); its gantry-main **Z arrows** (up = Z−, down = Z+, step from a short `kSteps` subset) go through `Workflow::JogGantryZ` and share the Jog window's `jogArmed_` flag, exposed there as the "Arm jog" checkbox. The Aux window's bottom-left **position plate** names where each stage stands — gantry-main / hex-left / hex-right, each device's live pose (`Workflow::DevicePose`, layer 2 does the fleet lookup) matched to the nearest saved position of that device via the shared `NearestSavedPos` (`core/SavedPositions.h`). Green when within 0.050 mm of it, amber with the distance otherwise; a device that is absent or disconnected drops off the list. Positions belong to the loaded product, so the same axis reading is a name under one product and unnamed under another. Hidden positions are candidates by default (the **+hidden** checkbox, persisted as `pos_labels_hidden`), because this answers where the stage *is* and naming a neighbour instead would be a lie — turning it off trades that for keeping the `algn_...` system names out of the plate. It is drawn straight onto the draw list, never into a child window, so it cannot swallow a click-to-move. Toggled by the "Positions" checkbox, persisted in `UiSettings`. The Aux plate also carries an **Autofocus** button + direction combo — the second launcher of the Camera tab's sweep (same App state, same `StartQuickAutoFocus`, same `jogArmed_` + `orch_.Busy()` gates); range and step stay in the Camera tab.
- **Image + overlay**: upload frame via `GlHost` textures, show with `ImGui::Image`, then draw vision overlays with `ImGui::GetWindowDrawList()` in the same screen coords. Keep textures in windows on the **main** GL context; ImPlot charts are pure vector geometry so they render in any viewport.
- **Log viewer** (`core/Log.{h,cpp}`): `Logger` ringbuffer, snapshotted by the UI with level filter + autoscroll.

**Why not raylib:** raylib is single-window by design (`InitWindow` once, one global GL context), so a real second OS window is impossible and ImGui multi-viewport can't be enabled through rlImGui. Owning a GLFW host removes that ceiling. Do not reintroduce raylib/rlImGui.
